# SoundBar 智能音箱 · 开发管理

> 用 GitHub 管一条硬件产品的完整开发链路：需求 → 声学 → 结构 → 固件 → App → 测试 → 量产。

## 这个仓库怎么用

| 你想做的事 | 用 GitHub 的什么 | 从哪进 |
|---|---|---|
| 记录一条需求 / 一个 Bug | **Issues** | 顶部 Issues 标签 |
| 看整体进度、排优先级 | **Projects 看板** | 顶部 Projects 标签 |
| 改一份文档 / 一份规格 | **分支 + Pull Request** | 见下方「改动流程」 |
| 定版发布（如 V1.0 固件） | **Tags + Releases** | 右侧 Releases |

## 改动流程（重要）

**不要直接改 main 分支。** 任何修改都走这条线：

1. 从 main 拉一条分支，命名如 `feat/声学规格`、`fix/蓝牙断连`
2. 在分支上改文件、提交（commit）
3. 发起 Pull Request，写清「改了什么、为什么改」
4. 审阅通过后合并回 main
5. 删掉这条分支

## 目录结构

```
.
├── README.md
└── docs/
    ├── 01-需求规格.md     # 产品要做什么
    └── 02-开发计划.md     # 里程碑与排期
```

## 里程碑

- [ ] **M1** 需求冻结（规格 + 目标价位确认）
- [ ] **M2** 声学方案定型（单元 + 功放 + 腔体）
- [ ] **M3** 结构与 ID 打样
- [ ] **M4** 固件 Alpha（蓝牙配对 + 多设备切换）
- [ ] **M5** App 联调
- [ ] **M6** 试产与验收

## 协作约定

- **提交信息**格式：`类型: 一句话说明`，类型用 `feat` / `fix` / `docs` / `test` / `chore`
  - 例：`docs: 补充频响曲线验收标准`
- **一个 Issue 只装一件事**，别把三条需求塞进一条
- 任务做完 → 关掉对应 Issue
